# Модель портала StepToLead: маркетинг клиента через гипотезы, все каналы на одном языке

Статус: согласованная модель (10.11.2026). Основа для всех следующих этапов. Заменяет
backend/app/domains/leadgen/SPACES.md (тот вёл к отдельному «миру аутрича» — так не делаем).

## 1. Главная мысль
Всё, что делает маркетолог, — гипотезы. Гипотеза = КОМУ (аудитория) + ЧТО (оффер) + ГДЕ (канал) + бюджет теста +
критерий успеха (цена лида / клиента, срок). Статусы: идея → тест → масштаб | стоп, в конце — вывод.
Каждая гипотеза отвечает деньгами: расход → отклик → лиды → квалифицированные → продажи → выручка.
Решение: окупается (цена клиента ≤ допустимой) — масштабируем, нет — стоп. Портал подсвечивает и то, и другое.

Директ, VK, Авито, Telegram Ads, 2ГИС, маркетплейсы, аутрич (письма/Telegram), сайт, SEO — всё это КАНАЛЫ одного
клиента и говорят на одном языке метрик. Аутрич — не отдельный продукт, а канал.

## 2. Что уже есть в коде (опираемся, не переписываем)
- Клиент `client_workspaces` → проекты `projects` (по умолчанию один) → источники/каналы `project_sources` с
  ежедневными метриками `source_metrics_daily` (расход, показы, клики, лиды, квал, продажи, выручка).
- Гипотезы `ad_hypotheses` (аудитория, оффер, посадочная, статус) ↔ рекламные кампании `ad_hypothesis_campaigns`.
- Лиды `client_leads` + атрибуция `client_lead_attributions` (канал, гипотеза, кампания, UTM), продажи
  `client_sales`, CRM (воронки `crm_pipelines`, сделки, задачи), экономика `project_economics.allowable_cac`.
- План работ и цели месяца (`projects.portal_state.launch`), роли сотрудников клиента, еженедельный отчёт.
- Лидогенерация/аутрич (`lg_*`) уже привязаны к `workspace_id`, но сейчас работают только в пространстве агентства
  (`settings.agency_workspace_id`) и живут вне цепочки выше.

## 3. Решения
1. **Агентство — клиент №0.** StepToLead — обычный клиент портала. Его аутрич и реклама идут той же цепочкой.
   Особые ветки «режим агентства» в коде уходят (остаётся только: кто администрирует портал).
2. **Направления клиента — воронки CRM** (а не отдельные проекты). У OneSpot: доступ к Telegram Ads, оплата
   кабинетов, биржа маркетологов — разные воронки одного клиента. Гипотеза и канал указывают воронку, куда идут
   их лиды; экономика (допустимая цена клиента, средний чек) — по воронке. Проект остаётся один по умолчанию.
3. **Паспорт клиента** — одно место знаний: продукт(ы) по воронкам, ЦА, офферы, УТП, что НЕЛЬЗЯ обещать, тон,
   от чьего имени пишем (компания, имя, подпись, сайт). Используется везде: ИИ-оценка баз (сейчас портрет ЦА лежит
   в настройках лидогена — переезжает сюда), тексты писем и объявлений, ИИ во входящих, персонализация.
4. **Каналы — модули** (как источники компаний в лидогене): пишутся в коде один раз и умеют
   (а) подтягивать метрики (API площадки, свои таблицы — у аутрича, или ручной ввод),
   (б) атрибутировать лиды (гипотеза, кампания, для аутрича — кампания и шаг письма),
   (в) показывать свои настройки. У клиента — «Подключить канал».
   **Аутрич** — модуль: внутри базы, рецепты, ящики и прогрев, цепочки, входящие — в пространстве клиента.
5. **Гипотезы** — рабочий экран маркетолога по клиенту: доска «идея → тест → масштаб / стоп» с цифрами против
   критерия. Гипотеза привязана к тому, что её реализует: рекламные кампании или кампании аутрича (база по рецепту +
   цепочка). Существующие `ad_hypotheses` расширяются до общих гипотез (канал, воронка, бюджет теста, критерий,
   срок, вывод), рекламная привязка сохраняется.
6. **Лиды — в воронку клиента.** Ответ на письмо с меткой «интересно» = лид с атрибуцией «аутрич → гипотеза →
   кампания → шаг». Где живёт лид — настройка клиента:
   - наша CRM (как сейчас);
   - **внешняя CRM** (у OneSpot — их CRM): модуль «Внешняя CRM» — передача лида и **обратная загрузка статусов
     и суммы** (иначе цену продажи не посчитать). Адаптеры: amoCRM, Битрикс24, универсальный webhook (лид — наружу,
     статусы — к нам на защищённый адрес). Лид всё равно хранится у нас (для аналитики) с внешним id.
7. **Деньги — полная цена клиента:** рекламный бюджет + расходы канала (подписки, данные: XMLStock, DaData,
   Checko; ящики, домены) + работа агентства (фикс в месяц на канал или на клиента — настройка). Всё это — расход
   канала по дням, чтобы аналитика считала CPL/CAC одинаково для всех каналов.
8. **Ресурсы:** общие агентства (ключи данных, прокси, ИИ) работают у всех клиентов, расход считается по клиенту;
   у клиента можно задать свой ключ. Свои всегда: рекламные кабинеты, домены и ящики, бренд, стоп-лист.
   Жалобы и несуществующие адреса — ещё и в общий стоп-лист (репутация почты общая).
9. **Клиент видит портал:** режим просмотра — доска гипотез, результаты по каналам и воронкам, отчёты, ответы
   аутрича (без доступа к настройкам и базам). Роли клиента уже есть — добавить доступ к разделу «Маркетинг».
10. **Шаблоны клиентов:** «Сохранить клиента как шаблон» (каналы, заготовки гипотез, рецепты баз, цепочки,
    отчёт) → новый клиент из шаблона в пару кнопок. Это копирование данных, не код.
11. **Ритм:** экран «Сегодня» по всем клиентам (горячие ответы, заявки без ответа сверх нормы, кончилась база или
    бюджет, отклонена модерация, упал прогрев, гипотеза вышла за критерий); еженедельный отчёт клиенту по гипотезам
    (что тестировали, цифры, решение); план-факт месяца.
12. **Переключатель клиента** в разделах, где работа идёт «внутри клиента» (лидогенерация, аутрич, гипотезы);
    плюс сводный режим «Все клиенты» там, где это полезно (Сегодня, входящие).
13. **`client_project_id` — заморожен.** «Аутрич как услугу» от 29.10 (кампания, ящик и стоп-лист клиента в
    пространстве агентства с `client_project_id`) не развиваем: новые клиенты работают в своём пространстве.
    Старый механизм продолжает работать как есть до этапа 3, где кампании и ящики клиентов переезжают в их
    пространства, а колонки и ветки `client_project_id` уходят.
14. **База компаний у каждого клиента своя.** Повторная оплата данных дешевле риска смешать клиентов; общий кэш
    публичных фактов по ИНН и домену — позже. Свои ключи источников у клиента — отложено.
15. **Основные домены пространства** — настройка (по умолчанию домен из поля «сайт»): с них холодные письма не
    шлём. Ящик принадлежит одному пространству.

## 4. Инварианты
- Данные клиентов не смешиваются нигде: списки, выгрузки, аналитика, входящие, ИИ-контекст.
- Ничего, что отличает клиента, не пишется в код — только данные и настройки.
- Не ломать: /api/portal/inbound/{token}, текущие статусы лидов, работу CRM и отчётов существующих клиентов,
  отправку и прогрев (меняется только, откуда берётся пространство).
- Храним только общие контакты компаний. Ключи — только через настройки портала, шифрованно. .env не трогать.

## 5. Порядок
Принятый план с разбором «модель против кода» — docs/PLAN.md (внешняя CRM идёт раньше доски гипотез).
Ниже — исходный черновик.
1. Клиент №0 и пространство клиента для лидогена/аутрича: workspace из выбранного клиента, перенос настроек
   агентства, ключи источников «агентства по умолчанию + свои», учёт расхода по клиенту.
2. Паспорт клиента (+ перенос портрета ЦА), переменные отправителя в письмах.
3. Аутрич как канал: project_source аутрича, расход канала по дням, «интересно» → лид с атрибуцией в воронку.
4. Общие гипотезы и доска; привязка кампаний аутрича; критерии и подсветка.
5. Внешняя CRM: webhook + amoCRM/Битрикс24, обратные статусы.
6. Режим просмотра для клиента, еженедельный отчёт по гипотезам.
7. Шаблоны клиентов, «Сегодня» по всем клиентам, рецепты поиска, новые источники (маркированная реклама в
   Telegram/VK, карта присутствия).
