# План реализации модели портала (docs/MODEL.md)

Статус: принят 10.11.2026. Порядок этапов отличается от черновика в разделе 5 MODEL.md: внешняя CRM идёт раньше
доски гипотез — без обратных статусов цену клиента у OneSpot не посчитать.

## Правила на все этапы
- Запрос к лидогену/аутричу без указания клиента работает как раньше — в пространстве агентства.
- Не трогаем: /api/portal/inbound/{token}, статусы лидов, структуру CRM, .env/.env.prod.
- Схема обновляется через backend/app/db_upgrade.py (Alembic нет), только добавлением.
- Ничего, что отличает клиента, в код не пишем — только данные и настройки.
- База компаний у каждого клиента своя. Общий кэш публичных фактов по ИНН и домену — позже.
- Свои ключи источников у клиента — отложено; общие ключи агентства работают у всех.

## Где модель не сходилась с кодом (разбор 10.11.2026)
1. В коде уже есть «аутрич как услуга» (29.10): кампания клиента живёт в пространстве агентства с
   `client_project_id` (lg_campaigns, lg_mailboxes, lg_dnc), база общая с агентством. Решение: побеждает
   «пространство = клиент»; `client_project_id` заморожен (работает как есть), убираем на этапе 3.
2. Два пути «лид в CRM»: агентство — сделка до ответа в проекте «Аутрич» (`outreach.hand_off`); клиент — сделка
   по ответу в воронке его проекта (`client_outreach.hand_to_client`). Единственным станет второй (этап 3).
3. Настройки лидогена были одни на портал (`leadgen:settings`), `lg_sources` — глобальная.
4. Прогрев считает пул по пространству — клиент с 2–3 ящиками сам себя не прогреет (этап 1Б).
5. `bounced` / `legal` в стоп-листе действуют только внутри пространства (этап 1Б).
6. Агентское в коде: запрет @steptolead.ru, этап «Тест портала», признак «тест портала» в hot.py,
   DEFAULT_ICP, подпись «Аутрич StepToLead».
7. Воркеры не смотрели на статус пространства — удалённый клиент продолжал бы рассылку.
8. Фактический расход на данные не писался (cost_rub = 0), была только оценка до запуска.
9. Экономика — одна строка на проект (`project_economics`), по воронке её нет (этап 5).
10. Заявки гипотезы считаются через `lead_inbound_sources` — лид аутрича в цифры не попадает (этапы 3, 5).
11. Аналитика стоит на `crm_deals` и `analytics_type` этапа — лиду во внешней CRM нужна сделка-зеркало (этап 4).

## Этапы

### 1. Пространство клиента в лидогене и аутриче
Статус: сделан 11.11.2026 (код и тесты; на прод не выкачен). Пространство запроса хранится в ContextVar
(`space.bind` на роутерах), поэтому сами ручки не менялись.
- `domains/leadgen/space.py`: пространство из заголовка `X-Workspace-Id` или параметра `ws`, иначе агентство;
  клиент должен существовать и быть активным. `GET /api/admin/leadgen/spaces` — список для переключателя.
- Все ручки /api/admin/leadgen/* берут пространство из зависимости, а не из `settings.agency_workspace_id`.
- Настройки лидогена — по пространству: ключ `leadgen:settings:{id}`; старый `leadgen:settings` один раз
  копируется в ключ агентства (старый остаётся для отката). Портрет ЦА по умолчанию уезжает в настройки агентства;
  у нового клиента портрет пуст, ИИ-оценка недоступна, пока не заполнят.
- Настройка пространства «основные домены» (по умолчанию — домен из поля «сайт» клиента): с них холодные письма
  слать нельзя. Ящик, подключённый у одного клиента, нельзя подключить у другого.
- Воркеры (цепочки, опрос ящиков, прогрев) пропускают неактивные пространства; шаги откладываются, не теряются.
- Ссылки на входящие (Telegram о горячих ответах, индикатор задач) — с `ws`; в тексте — имя клиента.
- Журнал расходов `lg_spend` (клиент, дата, источник, единицы, рубли, запуск) — пишется по завершении запуска.
- Фронт: переключатель клиента в разделах «Лидогенерация» и «Аутрич», заголовок в запросах, `ws` в ссылках.
- Старый механизм `client_project_id` работает как есть. jobradar остаётся в пространстве агентства.

### 1Б. Прогрев и общий стоп-лист
Статус: реализовано 17.11.2026, без выката на прод.
- Активные ящики с включённым прогревом из действующих пространств участвуют в общем пуле по умолчанию.
  Флаг `warmup_shared_pool` можно выключить у отдельного ящика: останется прогрев только внутри его пространства.
  Пары одного домена исключаются, в том числе для запланированных ответов. Лимиты, расписание и тексты
  не менялись. Холодные письма по-прежнему отправляются только внутри своего пространства.
- На экране прогрева видны только свои адреса; чужие ящики учитываются обезличенно как партнёры по прогреву.
  Межклиентский прогрев распознаётся по сохранённому Message-ID и не попадает во входящие аутрича.
- `unsubscribed`, `bounced` и `legal` для email и доменов действуют во всех пространствах; обычный отказ
  остаётся локальным. Правила применяются и к ранее сохранённым записям. На экране есть пометка «общий»
  и фильтр; записи из других пространств доступны только для просмотра, без внутренних заметок.

### 2. Паспорт клиента
- Одно место знаний: продукты по воронкам, ЦА, офферы, УТП, что нельзя обещать, тон, от чьего имени пишем.
- Портрет ЦА переезжает из настроек лидогена; переменные отправителя в письмах.

### 3. Аутрич как канал
- Единый путь «ответ → лид в воронку клиента» для любого пространства, включая агентство.
- `project_source` аутрича, атрибуция лида (кампания, шаг письма), расход канала по дням из `lg_spend`,
  ящиков, доменов и работы агентства (фикс на клиента, опционально на канал).
- `client_project_id` убираем: кампании и ящики клиентов переносим в их пространства.

### 4. Внешняя CRM
- Универсальный webhook: лид наружу, статусы и сумма — к нам на новый защищённый адрес; у нас сделка-зеркало
  с сопоставлением статусов. Затем адаптер CRM OneSpot (amoCRM / Битрикс24 — уточняется).

### 5. Гипотезы и доска
- `ad_hypotheses` → общие гипотезы: канал, воронка, бюджет теста, критерий, срок, вывод; связь с кампаниями
  аутрича; экономика по воронке; подсветка «окупается / стоп».

### 6. Режим просмотра для клиента
- Раздел «Маркетинг» в ролях клиента: доска гипотез, результаты по каналам, ответы аутрича; еженедельный отчёт.

Порядок: проверить и выкатить этап 1 → A → B → C → D.
- **A. Инфраструктура** (docs/TELEGRAM_INFRA.md): массовое добавление прокси с проверкой и внешним IP, один статус на
