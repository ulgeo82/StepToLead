## A. Пул прокси и Telegram-профиль клиента (`kind="telegram_user"`)

Цель: клиент подключает рабочий Telegram-аккаунт (не бота) к своей компании; переписка идёт через портал. Из России MTProto не работает, поэтому каждый профиль ходит через SOCKS5-прокси из пула.

### Пул прокси
- Модель `Proxy` (`app/models/proxy.py`) уже есть и используется агентскими аккаунтами (`TelegramAccount`, рассылки). Добавь поля:
  - `pool: str` — `"agency"` (по умолчанию, существующие записи) | `"client"`;
  - `max_accounts: int = 3`;
  - `dedicated_workspace_id: int | None` (FK `client_workspaces.id`) — выделенный IP компании.
- Выбор прокси при подключении профиля:
  1. если у компании есть прокси с `dedicated_workspace_id == workspace_id` — берём его (лимит тоже действует);
  2. иначе — прокси `pool="client"`, `dedicated_workspace_id IS NULL`, статус рабочий, число привязанных профилей `< max_accounts`; берём наименее загруженный;
  3. если подходящего нет — канал в статусе `waiting_proxy`, уведомление агентству в мониторинг (`services/monitor.py`, «Нет свободных прокси для Telegram-профилей»).
- **Закрепление навсегда:** `config.proxy_id` у канала не меняется автоматически никогда (Telegram подозрительно относится к смене IP). Переназначение — только вручную в админке, с предупреждением.
- Проверка здоровья прокси раз в 5 минут (TCP/SOCKS-рукопожатие до DC Telegram `149.154.167.50:443`). Упал → `status="error"`, `last_error`, алерт в мониторинг один раз; его профили видят в «Каналах» статус «Нет связи через прокси».
- Админка `/admin/proxies`: колонка «Пул» (агентство/клиенты), «Загрузка» `2/3`, «Выделен для» (компания). В карточке клиента в админке — переключатель «Выделенный IP для Telegram» с выбором прокси из пула клиентов.

### Подключение профиля (CRM → Чаты → «⚙ Каналы» → «Telegram-профиль»)
- Шаги: номер телефона → код из Telegram → пароль двухэтапной защиты (если включена). Переиспользуй паттерны `services/telegram.py` (`make_client`, `proxy_config`, `request_login_code`, `confirm_login`), но **не используй таблицу `TelegramAccount`** — это агентские аккаунты. Сессия (StringSession) хранится зашифрованной в `MessagingChannel.secret_encrypted` (тем же шифрованием, что и токены каналов).
- `config`: `{phone, telegram_user_id, username, proxy_id, mode}`.
- Режим `mode`, выбирается при подключении и меняется в настройках канала:
  - `"corporate"` (по умолчанию) — каждый новый личный диалог = заявка в «Неразобранном» (существующий поток `inbound`);
  - `"personal"` — подтягивать только диалоги с людьми, чей телефон или @username уже есть в контактах CRM этой компании; остальное игнорировать.
- Брать только личные чаты с людьми: группы, каналы, боты, «Избранное», служебные уведомления Telegram — игнорировать.

### Приём и отправка
- Для Telethon нужны **постоянные соединения**, а не переподключение каждые 15 секунд (частые переподключения подозрительны). Сделай менеджер клиентов: один лидер-процесс держит соединения всех активных профилей (лиз в Redis — как `tg_bot.py`, ключ свой), обработчики `events.NewMessage` для входящих и исходящих (исходящие с телефона тоже пишем в историю как `out`), `catch_up=True`, переподключение с экспоненциальной паузой.
- Отправка из портала — обычным текстом. **Никаких искусственных лимитов на сообщения.** Ошибки Telegram:
  - `FloodWaitError` → менеджеру понятная ошибка «Telegram ограничил отправку до HH:MM» (время по Самаре/зоне компании), уведомление владельцу и РОПу (роль `sales_head`);
  - `PeerFloodError` (спамблок) → «Telegram временно запретил писать новым людям с этого аккаунта (спамблок)», то же уведомление;
  - `AuthKeyUnregistered`/`SessionRevoked` → канал `status="error"`, «Сессия завершена — подключите профиль заново».
- `lookup`: по телефону — `ImportContactsRequest` (после поиска контакт можно не удалять), по @username — `ResolveUsernameRequest`. `history` — последние 50 сообщений диалога.

### Тесты
Подменяй Telethon-клиент заглушкой. Проверить: выбор прокси (лимит 3, выделенный, «нет свободных»), закрепление при повторном подключении, фильтр режима `personal`, игнор групп/ботов, обработку FloodWait/PeerFlood, что лидер один.

## B. «Найти и написать» из сделки

- В карточке сделки (`frontend/components/crm/deal-card.tsx`), блок «Переписка»: если у сделки/контакта нет диалога — кнопка **«Найти и написать»**.
- Backend: новый эндпоинт в роутере переписок (не в crm.py), например `POST /crm/deals/{deal_id}/reach/lookup` → берёт телефоны, @username и email контакта сделки, опрашивает **все активные каналы компании**, у адаптеров которых есть `lookup`, параллельно, с таймаутом 10 с на канал. Ответ: список `{channel_id, kind, name, found, title, has_history}`.
- `POST /crm/deals/{deal_id}/reach/open` `{channel_id}` → создаёт (или находит) `Conversation`, привязывает к контакту и сделке, если `has_history` — подтягивает `history()` в сообщения диалога, возвращает id диалога; UI открывает чат прямо в карточке, менеджер пишет первым.
- Если подключены только бот Telegram и/или Авито — показать: «Через бота и Авито нельзя написать первым. Подключите Telegram-профиль, WhatsApp или MAX».
- Права: доступно тем, кто может видеть сделку и писать в чат (используй существующие проверки доступа к сделке).
- Тесты: найден в нескольких каналах, не найден нигде, только бот/Авито, повторное открытие не создаёт дубль диалога.

## C. Почта как канал (`kind="email"`)

- Подключение: email, IMAP-сервер/порт, SMTP-сервер/порт, логин, пароль приложения (шифровать как секреты каналов). Пресеты: Яндекс, Mail.ru, Gmail. Кнопка «Проверить» — логин в IMAP и SMTP.
- Переиспользуй транспорт из `backend/app/domains/leadgen/sequences.py` (SMTP/IMAP в отдельном потоке) — импортируй, не меняй его поведение для лидогенерации.
- Приём: раз в 60 с, только `INBOX`, новые по UID (курсор в `config`). Диалог = адрес отправителя (`external_chat_id = email` в нижнем регистре). Из тела — текст без цитаты предыдущих писем; HTML → текст. Вложения в v1 — только имена файлов в тексте сообщения.
- Отправка: ответ в той же цепочке (`In-Reply-To`, `References`, тема `Re: …`), обычный текст + подпись менеджера из настроек канала.
- Новый отправитель → заявка в «Неразобранном» (как у других каналов). Рассылки, `noreply`, автоответы (`Auto-Submitted`, `List-Unsubscribe`, `Precedence: bulk`) — игнорировать.
- `lookup` по email: найден всегда, если адрес валидный (написать можно любому); `has_history` — есть ли письма от/к этому адресу в INBOX/Отправленных.
- Тесты с подставным транспортом: приём, дедупликация по Message-ID, игнор рассылок, ответ в цепочку.

## D. Правила на новую заявку и ИИ-автоответ

Расширь `backend/app/services/crm_automation.py` и UI `frontend/components/crm/automations.tsx`.

### Новые триггеры
- `INBOUND_MESSAGE` — входящее сообщение в любом канале. Условия: каналы (список kind/конкретных каналов), «только первое сообщение клиента», время: «всегда / рабочее время / нерабочее время» (рабочие часы — из существующих настроек SLA/воронки).
- `NO_REPLY` — клиент написал, менеджер не ответил N минут (N в правиле, по умолчанию 10).

### Новые действия
- `SEND_TEMPLATE` — текст с подстановками `{имя}`, `{компания}`, `{менеджер}`.
- `AI_REPLY` — ИИ пишет ответ по базе знаний компании (Настройки → Подключения → «ИИ-ассистент»; использовать `services/ai.py`: `complete`, `suggest_prompt`/база знаний). **По умолчанию отправляет сам** (режим правила `auto`; второй режим — `draft`: черновик в поле ввода менеджера).

### Защита
- Не более **2 сообщений ИИ** в диалоге подряд до ответа живого менеджера; после ответа менеджера счётчик сбрасывается.
- ИИ не называет цены, сроки, скидки и условия, которых нет в базе знаний; при вопросе о них — «уточню у менеджера». Температура низкая.
- Склейка: ждать 20–30 с после входящего (клиент часто пишет несколькими сообщениями), отвечать один раз на пачку.
- Сообщения ИИ и шаблонов помечаются `meta={"auto": "ai"|"template", "rule_id": ...}` и в чате видны с меткой «ИИ»/«Автоответ».
- Автоответы **не запускают** триггеры повторно (нет циклов) и не сбрасывают SLA менеджера: скорость реакции считается по первому ответу живого человека.
- Если ИИ не настроен (нет ключа) — `AI_REPLY` пропускается с записью в журнал правила; если в правиле указан запасной шаблон — отправить его.
- Выключатель на уровне канала: поле `MessagingChannel.ai_mode` (`off|suggest|auto`) уже есть — правило с `AI_REPLY` не срабатывает в канале с `ai_mode="off"`.
- Рекомендуемые правила (кнопка «Рекомендуемые правила» уже есть) — добавь: «Автоответ ИИ в нерабочее время», «Держащее сообщение, если менеджер молчит 10 минут».

### Тесты
Первое сообщение/не первое, рабочее/нерабочее время, лимит 2 сообщения ИИ, сброс после ответа менеджера, склейка пачки, отсутствие циклов, SLA не сбрасывается автоответом, ИИ не настроен → шаблон.
